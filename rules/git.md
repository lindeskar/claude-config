## Commits

- Conventional commit messages, single line: `<type>[scope]: <description>`
- Append `!` after `<type>[scope]` for a BREAKING change — but `!` means the **released artifact** breaks for its consumers (removed CLI flag, changed API), not that the change needs careful operational sequencing. CI-template flips, config changes, and rollout steps are NOT breaking; express sequencing in the PR body or merge gate. A spurious `!` forces a major bump of an artifact that didn't change.
- **Pick the commit/PR type by *consumer impact of the released artifact*, not by which paths changed.** In a repo that *publishes* something others consume — a reusable workflow (`on: workflow_call`), a composite action, or a served config artifact — a behaviour change is `fix:`/`feat:` even though it edits `.github/workflows/` or a `*.json`. `ci:`/`chore:` is only for *this repo's own* plumbing that nothing downstream consumes. The published artifact isn't always code: `annotell/renovate-config` ships the Renovate preset every repo's bot consumes, so any `packageRule`/`logLevelRemap`/cooldown change that alters bot behaviour is `fix:`.
- **On release-please repos, getting that type wrong bites twice.** `ci`, `chore`, `docs`, `refactor` and friends are **hidden types**: they render no changelog section, so the empty-changelog gate aborts the release PR and **no version is cut** — a consumer-facing fix mislabeled `ci:` lands on `master` but ships to nobody. Squash-merge uses the *PR title* as the commit, so the PR title is what gets classified. Mechanics: work-wiki memory `release-please-commit-type-visibility`.
- Never amend commits.
- **Never force-push.** When a task seems to require it (rebasing a pushed PR branch), use `git merge --no-ff <other-branch>` and push normally. This is absolute — no carve-out, not even for rewording a commit on your own fork's branch whose PR has no reviews. When a force-push is genuinely the only fix (a CI check rejecting an issue-closing keyword in a message), make the reworded commit locally and hand the user the exact `git push --force-with-lease origin <branch>` to run.
- **On a stacked PR, origin rewrites *your* branch when the branch below it is rebased** — so a follow-up push is rejected with `fetch first` and the fetch reports `(forced update)` on a branch you never force-pushed. Don't merge and don't force-push: `git fetch`, confirm origin's copy still carries your earlier work (`git diff <your-last-sha> origin/<branch> -- <files you touched>` should be empty), `git reset --hard origin/<branch>`, then cherry-pick only your new commits. Renovate rebasing its own bump branch is the usual trigger.
- **After resolving conflicts, verify the resolved content for your intended values — `rerere` silently applies *stale* resolutions.** It replays a previous resolution keyed on the conflict's textual shape, so when an earlier resolution settled one axis (field *order*) and a later conflict on the same hunk also carries a *value* change (a version pin), rerere reuses the old one and **drops your value change** — leaving no conflict markers, so nothing flags it. Tell: `Resolved '<file>' using previous resolution` in the merge output. Always `git diff origin/master…HEAD -- <files>` or grep for the values you intended before committing the merge.
- Never use `git -C <path>` — always `cd` to the repo directory first.
- Run `git add` and `git commit` as separate Bash calls, never chained.
- **Scope `git commit` with an explicit pathspec (`git commit <paths> -m …`) whenever the repo might carry unrelated staged or uncommitted changes** — a bare `git commit` lands the *entire* index, not just what you `git add`ed, and can sweep the user's in-progress work into your commit. When unsure, `git status --short` first; recover a bad bundle with `git reset --soft HEAD~1`.
- For multi-line commit messages, pass a multi-line string directly to `git commit -m` — never command substitution.
- Match commit granularity to the task — bulk-adding new files is one commit, not one per directory. Split only when changes are incremental and benefit from independent review or rollback.
- `git pull --ff-only` / bare `git fetch` **fails on repos that move a floating major tag** (release-please action repos like `annotell/gha-golang` republish `v1` per release): `! [rejected] v1 -> v1 (would clobber existing tag)`. Resolve with `git fetch origin --tags --force`, then pull — `--force` only repoints the floating tag. `--no-tags` does not help.

### Signing

- **Commit signing and SSH transport fail independently — a dead 1Password agent does not block pushing.** When the agent stops responding, `git push` over `git@github.com` dies with `sign_and_send_pubkey: signing failed` → `Permission denied (publickey)` while `git commit` still signs fine (and vice-versa). Don't treat this as blocked: push the already-signed commits over HTTPS with `git push "https://x-access-token:$(gh auth token)@github.com/<owner>/<repo>.git" <branch>` (a sanctioned command-substitution case). Diagnose which half is broken with `ssh -T git@github.com`.
- **Never `git commit` with `run_in_background: true`** — 1Password signing needs an interactive prompt; backgrounded commits fail with `failed to fill whole buffer`. Same reason a dispatched **subagent** can't make signed commits: in subagent-driven flows the controller commits in the foreground. **In a headless or background job even a foreground commit can fail intermittently** (`failed to fill whole buffer`, `1Password: agent returned an error`). For a throwaway branch `--no-gpg-sign` is acceptable; for anything landing in history, retry once and otherwise ask the user to run it — the identical commit typically succeeds later, so re-offer rather than declaring it blocked.
- **That failure is also silent — a bg-job commit can succeed yet be unsigned.** Verify with the right check: `git log --show-signature` / `%G?` are unreliable here (they error on a missing `gpg.ssh.allowedSignersFile` and report `No signature` even for correctly signed commits). The reliable local check is the header: `git cat-file -p HEAD | grep '^gpgsig'`. Only report Unverified when it's genuinely absent.
- **Always create commits with a local, signed `git commit` — never via the GitHub API.** API-created commits (`gh api --method PUT .../contents/...`) land **Unverified**. Don't script API commits to save cloning for multi-repo changes — clone each target locally (usually already under `~/Code/_kognic/`), branch, edit, commit signed.

## Pull requests

- **Create PRs as draft and leave them draft — flipping to ready (`gh pr ready`) is the user's call, never yours.** `gh pr create --draft --title "..." --body "..."` with a description; no exceptions, even throwaway PRs. The draft state is not merely a wait-for-CI device, so **green CI is not a licence to un-draft**: a ready PR fires CODEOWNERS review-requests and spends someone else's attention. Nor is "the user asked for this work now" — that authorizes writing the change, not soliciting review of it. If you judge it reviewable, say so in your report and let the user flip it.
- **Pass `--base` explicitly when the repo's base branch isn't its default** — `gh pr create` silently targets the default branch. **`annotell/frontend-annotation` → `--base next`.**
- **A PR title that fails validation is fixed in place with `gh pr edit --title`** — no close/reopen, no empty commit. The `annotell` org's "Validate PR title" check is served by the `kognic-github-app` over webhooks, so it re-evaluates immediately on a title edit. Allowed types: `feat`, `feature`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. A repo's own history may use a type the check rejects, so don't infer the allowed set from `git log`. For titles containing `!`, set the title via the API from a Write-created file.
- **Before pushing a new commit to an open PR, check its review state** (`gh pr view <n> --json reviewDecision`) — a push to an `APPROVED` PR dismisses the approval and forces re-review. Not a hard no, but never do it unprompted: ask first. Often the better move is to merge as-is and open a follow-up PR. Editing the body or title does NOT dismiss approval; only new commits do.
- Add the `autoreview` label to PRs that only touch staging environments in `kognic-cd`, `k8s-platform-gitops`, or `k8s-platform-gitops-volcano`. Never on PRs touching prod paths.
- **A throwaway change added only to trigger CI must be reverted the moment CI confirms green** — before the PR is marked ready, never left with a "remove before merge" marker. Squash-merge folds every commit on the branch in, so the marker doesn't stop it landing. If the trigger must survive the review window, revert it in a second commit on the same branch.
- **Closing a PR/issue with a comment: post the comment first, then close.** `gh pr close`/`gh issue close` accept only `--comment <string>` — no `--body-file` — which tempts a banned command substitution. Two calls instead: `gh pr comment <n> --body-file <path>`, then `gh pr close <n>`.
- **Scope a consumer PR to the behaviour change — let Renovate own version bumps — and check for in-flight PRs on the same lines before branching.** Two conflict sources compound when you ship a shared artifact then migrate its consumers: *you* released the new version, so Renovate opens a bump PR in every consuming repo within hours (conflicting even when the bot picks the identical SHA — the collision is positional, not textual); and unrelated PRs may already be in flight on the exact lines you're editing. So bump only the refs your change needs, and run `gh pr list --repo <o>/<r>` plus `wt list` before `wt switch --create`.
- **When posting a code review as a PR comment**, wrap the body in a collapsible `<details><summary>Code review results</summary>` … `</details>` block (blank line after `<summary>` and before `</details>` so the markdown renders), keeping any `` `/anthropic-review-pr:review-pr` output: `` marker above the `<details>`. Write the body with **Write** (reviews routinely contain `!`) and post with `gh pr comment <n> --repo <o>/<r> --body-file <path>`.

## PR/issue bodies and links

- PR body: lead with the **intent** (why / what it achieves), not a diff recap. Default to one sentence plus any tracking link. Don't restate what the diff shows — no changed-file lists, counts, or before/after strings. Backticks for identifiers and paths. Add a second sentence only when the reviewer needs context invisible in the diff; use a `## Summary` bullet section only for genuinely multi-concern changes. **Cut anything no reviewer will act on or ask about** — merge-sequencing notes, mechanism walk-throughs, "how it works", hedged caveats, and the tool versions or sibling PRs you verified against (both go stale the moment either merges). If in doubt, shorter.
- Describe what changed, not what was intentionally omitted — don't enumerate non-changes unless the gap would surprise a reviewer.
- **Keep the body in sync when a follow-up commit changes behaviour it describes** (e.g. a default or value the body names). A body edit is free and doesn't dismiss approval.
- Readability: short, plain sentences; split run-ons; lead with the concrete cause a reader can picture; plain words over jargon. Separate distinct points (cause → fix → cross-reference) with blank lines, even in a 2-3 sentence body.
- **Cross-repo references — fully qualify, then format by surface.** Resolve the ref to the repo it actually lives in and verify that repo first; a bare or wrong-repo `#NNN` lands in the wrong number space, often on an unrelated item. Most plateng tracking issues live in `kognic-internal/devplat`, but not all. In **GitHub bodies and comments** paste the plain full URL (`https://github.com/owner/repo/pull/NNN`), optionally after a lead-in (`Tracked in …`) — GitHub renders it rich; do **NOT** wrap it in `[text](url)`. In **chat replies to the user** use a markdown link `[owner/repo#NNN](url)`, which a bare URL or inline-code ref won't render as clickable. For a file in another repo, paste the plain blob URL.
