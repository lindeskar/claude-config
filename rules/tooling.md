# Tooling

> War stories: `reference/tooling.md` (not auto-loaded). Kognic-specific procedures live in the work wiki, named inline below.

## Python / uv

- Always run Python via `uv run` (e.g. `uv run main.py`). Lockfile churn, cache corruption, and reproducing a CI env: `rules/python.md`, which loads when you open a Python file.

## Terraform / OpenTofu

- **`terraform` (HashiCorp) vs `tofu` (OpenTofu) — pick by repo; default `terraform`.** Only the **volcano estate** (`terraform-*-volcano`) runs `tofu`. Running the wrong one rewrites `.terraform.lock.hcl` into the other registry's namespace and can produce a lock CI rejects. Check with `grep -rE 'setup-opentofu|setup-terraform' .github/`. Estate split, plan-output enumeration, and lockfile regen: `rules/terraform.md`, which loads when you open a terraform file.

## Command sandbox

- Build caches are redirected globally via `settings.json`'s `env` block (→ fixed `/tmp/claude/*`). **Don't prepend per-command cache env prefixes** — run `uv`/`go`/`gh`/`npm` bare so `permissions.allow` patterns match. For an uncovered tool prefer a fixed `/tmp/claude/<tool>-cache` over `$TMPDIR`.
- `$TMPDIR` resolves differently in sandboxed vs non-sandboxed calls. When a temp file must cross calls with different sandbox settings, note the absolute path from the first call and reuse it verbatim.
- **Shell writes are blocked in more places than you expect** — the job tmp dir (`$CLAUDE_JOB_DIR/tmp`) despite the background-session prompt recommending it, and some config repos' own directories. The tell is `operation not permitted` on a redirect. Use `/tmp/claude/...`, pipe straight into the consumer instead of staging a file, or use the **Write** tool, which is not subject to this.
- **golangci-lint reports a false clean** when its cache write is blocked (macOS ignores `XDG_CACHE_HOME`; fact-based linters under-report silently). Tells: `persist facts`/`pkgcache` `operation not permitted` warnings, or nonzero exit alongside `0 issues.`. Re-run with `GOLANGCI_LINT_CACHE=/tmp/claude/golangci-cache`.
- `terraform`/`tofu` commands that launch a provider (`test`, `plan`, `apply`, `providers schema`) fail in-sandbox with `Unrecognized remote plugin message` — not a cache issue. `init` works sandboxed; run the rest with the sandbox off.
- `ps`/`pgrep` return no process list under the sandbox (`sysmon service not found`) — track a background command through its output file, not the process table.
- **Anything touching the Docker daemon is sandbox-blocked.** This hits whole `make` targets that wrap tools in containers rather than the tool itself — the helm-chart repos run `helm`/`helm-docs`/`kube-score` via `docker run`, so `make docs`/`lint`/`template`/`kube-score` need `dangerouslyDisableSandbox: true`. Read the Makefile for a `docker run` before assuming a target is a local binary.
- **Anything that authenticates through `gcloud` fails sandboxed, and reports it as a *credentials* error rather than a permission one** — the helper can't write its cache under `~/.config/gcloud` (`Unable to create private file … credentials.db`). So `crane`/`docker` against `*-docker.pkg.dev` dies with `error getting credentials`, and `kubectl` against GKE dies in `gke-gcloud-auth-plugin`; a cached token can make early calls work and later ones break mid-session. Re-run sandbox-off — read-only registry and cluster reads are safe there.
- **Multi-repo `git` over SSH inside a *script* is unreliable under the sandbox**: some repos' `fetch`/`push` fail while an *identical direct* Bash call succeeds, and in-script retries keep failing deterministically. That split is the tell — don't build retry loops, just re-run the script sandbox-off. Read-only `gh api`/HTTPS in a script is unaffected.
- **A `git push` wrapped by another tool is sandbox-blocked even as a direct call** — `gh` extensions that shell out to git (`gh stack link`/`push`/`submit`) fail under the sandbox while a bare `git fetch` over SSH in the same repo succeeds, so a working fetch doesn't clear the wrapped push. Tell: `nc: authentication method negotiation failed` / `Connection closed by UNKNOWN port 65535` — a transport error, not a permission one. Re-run sandbox-off.
- **Docker Desktop does not share `/tmp` — a `-v /tmp/claude/...:/src` mount is silently *empty*, not an error.** The tool then reports "nothing found" over an empty dir, which reads as a real result. Mount a path under `~/Code` instead, and prove a suspicious empty result with `docker run --rm -v "$PWD:/src" <img> ls -la /src`.
- A test that fails only under the sandbox but passes with it off almost always has a hidden external-network dependency — *not* a code regression, even next to recently-changed code. It can present as a plain assertion mismatch, not a permission error; CI-green-but-local-red is the tell. Fix by making the test hermetic, not by touching product code.

## Bash tool discipline

- Use built-in tools for all file operations — never shell equivalents: **Read** not `cat`/`head`/`tail`/`sed -n`; **Glob** not `find`/`ls`; **Grep** not `grep`/`rg`/`awk`; **Edit** not `sed`/`awk`; **Write** not `echo >`/`cat <<EOF`. Narrow exception: one mechanical, identical edit across many files may use a single `sed`/`perl -pi` pass, only when verified afterward by a compiler/linter/test or a zero-stragglers Grep — never for context-dependent edits.
- Never chain Bash commands with `&&`, `||`, or `;` — one command per call (includes `cd`, `git add` + `git commit`, multi-step inspection). Parallel *independent* calls in one message are fine, but they share one cwd — never fan out cross-repo git ops in one batch (a `git push` can silently run in the wrong repo).
- A dispatched sub-agent's Bash cwd does **not** persist between its calls (unlike the main session) — instruct sub-agents to use absolute paths, or `cd <abs> && <cmd>` in one call.
- Never use command substitution (`$(...)`/backticks) — capture output in a prior step, or use built-in tools. One exception: injecting a secret, e.g. `GITHUB_TOKEN=$(gh auth token)`, where substitution is required because a literal token gets blocked as credential leakage.
- **Interactive zsh mangles `!` via history expansion — even inside single quotes and quoted heredocs** (`feat!: x` → `feat\!: x`). It corrupts content written via `echo`/`cat`, CLI arguments (`gh pr create --title`), and inline `jq`/`python -c` programs (commonest trigger: `<!--…-->`). Use **Write** for any content containing `!` and pass it via `@file`; for inline programs, match a substring without the `!` or run from a Write-created file. Verify suspect output with `od -c`.
- **Interactive zsh does not word-split unquoted parameter expansions** (unlike bash): `set -- $var` leaves the whole string as one field, so every downstream call silently gets a malformed arg. Force splitting with `${=var}`, or avoid the pattern — prefer a `jq`-built list, an explicit array, or two parallel value lists. Tell: every iteration errors with the *concatenated* fields glued together.
- **Don't assign to zsh's special/read-only variables.** `status` is a read-only alias for `$?`, so `status=$(...)` fails with `read-only variable: status` and aborts the whole command — a CI-poll loop built on it dies on its first iteration. Same trap for `path`, `pipestatus`, `argv`, `PATH`. Just rename to `line`/`check`/`out`.
- **Quote glob metacharacters in Bash args — unquoted, zsh aborts the command before it runs.** A literal `*`/`?`/`[` that isn't a real path gets glob-expanded, and with no match errors `zsh: no matches found: <arg>` without running anything — `grep -rn foo --include=*.go .` dies on `--include=*.go`. Quote it: `--include='*.go'`. Hits any glob-shaped flag value and any URL with a query string. Prefer the built-in **Grep** tool (`glob:` param) when available.
- **Never bury a long wait inside one Bash call.** `sleep N && <cmd>` where N is near or over the 120s default timeout gets SIGTERM'd (exit 143) *before* `<cmd>` runs, so you wait the full timeout and get nothing. Keep the sleep well under 120s and poll in a separate short call, or run the wait with `run_in_background: true` and let the notification wake you.

## Verification & investigation

- **Validate YAML/JSON from Bash with `yq`** (`/opt/homebrew/bin/yq`), not a Python one-liner — the system `python3` has no `pyyaml`, and `uv run --with pyyaml` also fails. `yq '.jobs.x.steps[]|select(.id=="auth")' f.yaml` both proves the file parses and projects the field you want.
- **Don't comma-chain paths off a `yq` pipeline — `,` binds looser than `|`, so the later paths resolve against the *root document*, not the piped node.** `.a[]|select(…)|.x, .y` returns the root's `.y`, giving either a value from the wrong node or a `null` that reads as "field absent" — no error either way. Project the whole node instead (`yq -o=json '.a[]|select(…)'`) and read the fields off it.
- **Never discard stderr on a command whose *empty* output you intend to read as an answer** — `cmd 2>/dev/null | <parser>` turns "the command never ran" into "no results", and a *setup* failure (dependency resolve, auth, bad path) looks identical to a clean negative. Bites hardest when probing N variants at once: every probe comes back empty and reads as a finding about the thing under test. Keep stderr, or prove the harness works by including a probe you know must match.
- Use LSP diagnostics and go-to-definition to understand code — don't guess at types, imports, or call sites by grepping. On errors: LSP/compiler output first, then read the source.
- Before asserting a tool or system **can't** do something — especially into long-term memory or as fact to the user — verify against a concrete artifact (a real PR, CI run, log line, command output). Confident negatives extrapolated from related notes are how wrong facts get recorded.
- **"No conditionals" doesn't mean a value can't be derived — check for interpolation into a *name or reference* first.** Selecting one of N pre-declared blocks by an interpolated key is the standard substitute; it resolves at compile time and fails loudly on a bad key (GitLab CI: `extends: .base-$[[ inputs.TAG ]]`). Tell you got it wrong: you propose exposing the derived value as another caller-set input. The same escape hatch exists in Helm/Kustomize/GHA.
- **"Is A faster than B?" is cheap to measure — measure it**, don't reason from geolocation, whois, or hop count. Two hostnames can resolve to the same city and differ by orders of magnitude, and an extra proxy hop can be *faster*. Time the same payload against each, alternating. Case: work wiki `vecr-push-via-envoy-proxy`.
- **Never reason from recall about a version-specific constant, default, or diff — read it out of the source at the exact tag.** Recipes for both (`contents?ref=<tag>` fetch, checksumming files across two tags): the `github-api` skill. Matching an error string to an upstream issue tells you *a* mechanism that produces it, not that yours is the same one — check each candidate's own discriminator before naming a root cause.
- **Don't open a privileged channel into prod to observe something available locally or on the user's own screen.** `kubectl port-forward`/`exec` on a prod pod is a sensitive remote action and gets denied — and it's slower than reading the fact from the browser or a faithful local rebuild. Reserve it for facts that exist *only* in the cluster, and ask first.
- **"Can we X?" is a question, not an instruction to do X** — answer it, then ask. Bites hardest on live or shared systems, where acting removes the user's choice over timing and blast radius. Once the user says "ask before changing live config", that stands for every later change.
- **A steady *fractional* failure rate points at a load-balancer fan-out — count the backends before blaming the network.** A stable ratio (not bursts, not timeouts) implies per-connection selection across N backends of which M are bad. A TCP reset one RTT away is a rejecting backend, not transit; probing a parallel deployment on the same path exonerates the shared hops.
- A deployed change with **no observable effect** is a signal to find out *why it's inert* (config precedence, wrong scope, stale cache, not loaded) — not a cue to try the same setting elsewhere. Verify the **effective/resolved value** the process used, then read the source or issue tracker for the override mechanism. Case: work wiki `renovate-ce-config-precedence`.
- **Narrowing what a converging process writes creates a one-time transition burst — size it before rolling out.** A mirror/sync/reconciler that drops items from its scope must first *delete* everything it previously wrote, so the first run is proportional to accumulated history, not the small steady state (e.g. GitHub keeps `refs/pull/<n>/head` for every PR ever opened, so a mirror cleanup scales with total PR count, not open PRs — count it with `git ls-remote <url> 'refs/pull/*' | wc -l`). Get that number first, then check it against **every** ceiling it crosses: per-item budgets *and* whole-request duration/proxy timeouts. A steady state that fits comfortably says nothing about the transition, and "it converges eventually" can still mean each attempt fails and one item's failure aborts the rest of the run.
- When confirming a fix from a metric/log signal, the signal must be **specific to the path you changed**, not ambient traffic on a shared component. Pick a discriminator that was measurably different during the outage, and require a second independent signal to agree. Case: work wiki `o11y-loki-write-path`.
- **Diagnosing a delivery failure? Get the *sender's* record first — the receiver only logs what arrived.** Failures split into "never arrived" and "arrived and went wrong"; your logs hold only the second, so a receiver-side count measures the wrong population. Get the sender's delivery list (a GitHub App's Advanced tab, the provider's dashboard) and join on delivery id. Tell: you build a detailed mechanism from receiver errors and it explains only a minority of failures.
- **A shorter runtime only proves a speed-up if the work still happened.** Before reporting "N× faster", confirm the operation wasn't skipped — content-addressed uploads dedupe and build steps hit caches. Check that real bytes moved (layer/blob digests, cache-hit lines) rather than trusting the timer.
- **An "it isn't happening" negative is only as good as your discriminator — validate the filter fires for a known positive before asserting absence.** Red flag: repeating the same empty query while the user insists it happened — suspect your filter, not their report, and switch to a field you've *seen populated*. Technique: work wiki `external-idp-sso-onboarding` → "Debugging a login".
- **Delegating a "which of these N don't do X" sweep to a subagent? Give it known-positive *and* known-negative anchors and require both be reported.** An all-negative result is exactly the shape a silently-broken method produces, so "all clean" reads as a finding rather than a failure — anchors make the breakage self-detecting. Tell the sweeper *where* the fact must live so it enumerates authoritatively rather than relying on `gh search code`, which is index-lagged. Verify surviving positives yourself.
- A review subagent's findings are **claims to verify, not facts to relay** — before adopting a severity or repro, reproduce the exact trigger with a throwaway test, then delete it. Subagent exploit examples are often directionally right but imprecise, and the imprecision changes the severity.
- **"This test doesn't discriminate" is checkable in two calls: apply the mutant, confirm the *named* test fails, revert.** Better, skip the revert entirely — copy the artifact *and its test* into a scratch dir, mutate the copy, run the tool against that, delete the dir. Nothing was ever broken in the tree, so a left-behind mutant can't pass review as a green suite. Works wherever the tool takes a config/target path (semgrep, linters, generators). If you do mutate in place, prove the file is byte-clean afterwards (`git diff`) before running the suite or committing.
- **Verify a "this is a regression" claim by running the *base* version against the same probe — severity often collapses.** A reviewer comparing only the new artifact will report a gap as newly introduced; the old one frequently had the same gap, or the whole code path was already dead, making it an incomplete fix rather than a break. Cheap: check the base ref out beside the new one and run both over one file.
- **When a bug only manifests under condition X, a green check that doesn't reproduce X is not verification — say so, and name what would prove it.** A fix branched off the default branch usually runs *without* the trigger, so CI passes for the same reason it did before your change. Fixes for a not-yet-merged dependency bump are the standard case: verify on the *rebased bump*.
- **A test fake built from your own reading of a vendor SDK proves only that your code matches your assumption.** Take field names and response shapes from the real SDK/API (the installed package's model class, or one recorded live response), not from the calling code. Tell: the bug is a wrong attribute name or a fallback that never fires, and the test asserts the same wrong name.
- When a request says "all uses" / "everywhere" / a plural or glob, enumerate the full match set first and reflect the scope back before editing.
- When telling the user the exact invocation of an unfamiliar CLI, verify its flag convention (`--flag=value` vs `--flag value`) against `--help` first — many vendor CLIs only accept space-separated values.
- When wiring dynamic credential fetching (AWS `credential_process`, `op run`, assume-role helpers), check higher-precedence credential sources *first* — a leftover static entry silently wins and the helper never runs.
- When a build/lint **passes locally but fails in CI** (or vice-versa), suspect a **pinned-tool-version difference before the code** — find the version CI vendors (Makefile `*_VERSION`, action `with: version:`, `.tool-versions`) and reproduce with *that* binary. Case: work wiki `reference_k8s-gitops-ci-helm321-render`.
